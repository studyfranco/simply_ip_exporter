## `src/` — entry points

| File | Responsibility |
| :--- | :--- |
| `src/main.rs` | Process entry point. Loads `.env`, initializes `tracing`, reads `RuntimeConfig`/`INITIAL_MASTER_KEY`, connects the DB, runs migrations, builds the `SecretCipher`, runs `bootstrap_master_key` (mints and once-prints the Master key/signing secret if `api_keys` is empty; supports deterministic `INITIAL_MASTER_KEY`/`INITIAL_MASTER_SIGNING_SECRET` for CI), then `verify_encryption_key` (a canary decrypt of the Master key's sealed `signing_secret` — `SecretCipher::from_env` only checks the configured key is 64 hex characters, so a syntactically valid but *wrong* key would otherwise pass silently and only surface later as opaque per-request `401`s; this aborts boot loudly instead, `exit(1)` with an explicit log line), pins the Master identity via `MasterPin::pin_at_boot`, spawns the sync worker and the Vault-group-permission cleanup worker (`groups::spawn_group_permission_cleanup_worker`), binds the listener, and serves with graceful shutdown (`SIGINT`/`SIGTERM`, aborting both background workers). Has its own `#[cfg(test)]` module covering `verify_encryption_key`. |
| `src/lib.rs` | Library root (`#![warn(missing_docs)]`). Declares every module, the `MAX_REQUEST_BODY_BYTES` constant shared between the router's `DefaultBodyLimit` and `middleware::MAX_SIGNED_BODY_BYTES`, and `create_app(AppState) -> Router` — the single place the full route table is assembled (probes and `/feed/v1/*` outside `auth_middleware`; `/api/*` nested behind it; `static/` as the fallback service). |

## `src/` — shared foundations

| File | Responsibility |
| :--- | :--- |
| `src/state.rs` | `AppState`: the `Clone`-cheap bundle of `db`, `config`, `cipher`, `replay_guard`, `master_pin`, `ip_cache`, `rate_limiter`, `dns_resolver` (2026-08-25 — the `DnsResolver` shared with `config.trusted_proxies`, see `dns_cache.rs`), and an optional `vault_client`, threaded through every handler via Axum's `State` extractor. |
| `src/config.rs` | `RuntimeConfig::from_env()` and everything it depends on: `TrustedProxies`/`resolve_client_ip` (the `X-Forwarded-For`/`X-Real-IP` trust-boundary logic — headers are honored only from a configured trusted peer), `resolve_bind_addr`/`parse_bind_addr` (`BIND_HOST`/`PORT`), and `validate_initial_master_key` (the strict-hex, fail-closed check on `INITIAL_MASTER_KEY`). `TrustedProxies` (rewritten 2026-08-19, ported from `example/simply_ip_vault`/`example/simply_hook_executor`'s identical design — see `AGENT_NOTES.MD`): `ProxyMatcher::{Network, Hostname}` — a hostname/Docker container name (e.g. `traefik_tomidejetsu`) is accepted at parse time whether or not it currently resolves (only a genuinely malformed entry is fatal), then resolved through the shared `dns_cache::DnsResolver` (`resolved()`, awaited per request in `middleware.rs`/`feed.rs`) and a boot-time `prime_with_grace()` (resolves once immediately, retries once after a 60s grace period on a detached task, never blocks or fails startup on a DNS outage). As of 2026-08-25 the positive/negative-TTL caching logic itself lives in `dns_cache.rs` (extracted so `bound_ips` hostname support reuses it rather than reimplementing it) — `TrustedProxies` now just holds a `DnsResolver` and exposes `dns_resolver()` for `AppState` to clone. |
| `src/dns_cache.rs` | `DnsResolver` (2026-08-25, extracted from `config::TrustedProxies`): a positive/negative-TTL (`30s`/`5s`) cache mapping *arbitrary* hostnames — not a fixed, startup-known set — to their currently-resolved addresses, `resolve()`/`force_resolve()`. Also `lookup_hostname` (the raw `tokio::net::lookup_host` call, fails closed to an empty list) and `hostname_rejection` (the syntactic "is this shaped like a DNS name" check, shared verbatim by `config::parse_trusted_proxies` and `bound_ips::parse_bound_ips` so both settings accept exactly the same hostname shapes). `TrustedProxies` and every `bound_ips` check share one `DnsResolver` instance (`AppState::dns_resolver`, cloned from `TrustedProxies::dns_resolver()`), so a name referenced by both resolves once. |
| `src/bound_ips.rs` | `bound_ips` parsing/enforcement for `api_keys` and `endpoints` (2026-08-25 — hostname support, sharing `dns_cache::DnsResolver`). `BoundIpEntry::{Network, Hostname}`, `parse_bound_ips`/`validate_bound_ips` (the three-way CIDR/bare-address/hostname parse, mirroring `config::parse_trusted_proxies`'s shape), and the async `is_allowed(entries, client_ip, dns)` — resolving any hostname entries through the shared cache before matching. Used by `middleware.rs` (`api_keys.bound_ips`) and `feed.rs` (`endpoints.bound_ips`); `validate_bound_ips` replaces the old CIDR-only validator previously in `api/support.rs`. |
| `src/error.rs` | `AppError`, the single enum every handler returns via `Result<_, AppError>`, and its `IntoResponse` impl — the one place HTTP status codes and the `{"error": "..."}` envelope are decided. Includes `BodyRejected(StatusCode, String)`, which lets `src/extract.rs`'s strict extractors normalize a rejected request into this envelope while still passing through a non-`400` status (e.g. `413`) verbatim, `ConflictWithDetails { message, details }` (matching `example/simply_ip_vault`'s identical variant) — a `409` whose body merges structured machine-readable detail (e.g. the endpoints blocking a key delete) alongside `error` at the top level, matched ahead of the flat status/message table since it's the one variant whose body isn't just `{"error": ...}` — and `VaultNotConfigured`/`VaultUnreachable` (`503`/`502`, used by `api::groups::list_vault_groups`/`grant_key_group` when there's no Vault to ask or a live call to it fails). |
| `src/extract.rs` | `StrictJson<T>`/`StrictPath`/`StrictQuery<T>` (the last added 2026-08-19): wrappers around axum's built-in `Json`/`Path`/`Query` extractors that remap a rejection (malformed body, invalid UUID segment, malformed or unrecognized query parameter) through `AppError` instead of axum's own plain-text rejection body — closing a gap where a malformed request bypassed this service's error envelope entirely. `StrictQuery` only normalizes rejection *shape*; a query struct still needs its own `#[serde(deny_unknown_fields)]` to make an unrecognized parameter a rejection at all (see `api::audit::AuditLogQuery`). Used by every mutating handler in `api/keys.rs` and `api/endpoints.rs`, and by `api/audit.rs`'s query-string parsing. Has its own `#[cfg(test)] mod tests` exercising `StrictQuery` directly against hand-built `Parts` (no router needed). |
| `src/crypto.rs` | Two independent primitives sharing a file because they protect the same column (`api_keys.signing_secret`): `canonical_v1_payload`/`compute_signature`/`verify_signature` (the `CANONICAL_V1` HMAC-SHA256 scheme used both inbound and outbound), and `SecretCipher` (XChaCha20-Poly1305 sealing, keyed by `EXPORTER_ENCRYPTION_KEY`, with a plaintext fallback when unset). |
| `src/master.rs` | `MasterPin`: resolves and freezes the Master key's UUID once per process (`pin_at_boot` at startup; `resolve`/`authenticate` for on-demand use), so a direct-database `UPDATE api_keys SET is_master = true` on a different row cannot elevate that row without a restart. `pin_at_boot` checks the `master_marker` unique index via `crate::db::has_index` (not `sea_orm_migration::SchemaManager::has_index` — see `db.rs`'s entry for why). |
| `src/replay.rs` | `ReplayGuard`: an in-memory, self-pruning `HashMap` of recently-accepted `(key_id, digest)` pairs, enforcing single-use signatures within the `SIGNATURE_MAX_AGE_SECONDS` window. Bounded at 250k entries with backoff-limited sweeps under sustained saturation. |
| `src/db.rs` | `connect`/`run_migrations`/`apply_sqlite_pragmas`: builds the SQLite pool pinned to exactly one connection (`SQLITE_MAX_CONNECTIONS = 1`), declares `journal_mode=WAL`/`synchronous=NORMAL`/`foreign_keys=ON`/`busy_timeout` at connect time, and confirms them afterward. Also `has_index` (2026-08-18, ported from `example/simply_ip_vault`): a per-backend catalog query (`sqlite_master`/`pg_indexes`/`information_schema.statistics`) used by `master.rs::pin_at_boot` instead of `sea_orm_migration::SchemaManager::has_index`, which answers `BackendNotSupported` on PostgreSQL rather than correctly reporting the index. |
| `src/middleware.rs` | `auth_middleware`: the Axum middleware guarding every `/api/*` route. Resolves `state.config.trusted_proxies.resolved().await` first (a refcount bump when no `TRUSTED_PROXIES` hostname is configured; a possible DNS lookup, cached, otherwise), validates `X-Timestamp` before touching the database, looks up the key by `X-API-Key`, applies `MasterPin::authenticate`, verifies the mandatory `X-Signature-256` over the full request target, checks `ReplayGuard`, and only then evaluates `bound_ips` (async, via `bound_ips::is_allowed` against `state.dns_resolver` — 2026-08-25, hostname-aware) — cheapest-and-unauthenticated checks first, network authorization last. A `Content-Length` over the router's body limit is rejected as `413` before any of the body is read; the same limit hit mid-stream (a `Content-Length`-less chunked body) falls back to the same `413` via `to_bytes`'s own cap. |

## `src/` — in-memory cache, IP pipeline, and Vault sync

| File | Responsibility |
| :--- | :--- |
| `src/cache.rs` | `IpCache`: the `Arc<RwLock<HashMap<Uuid, EndpointCache>>>` at the center of the "zero disk wear" requirement. `apply_full`/`apply_diff` merge Vault's full/differential sync responses; `snapshot` returns an endpoint's current live networks; `full_sync_due` tracks the 24h full-resync clock in-process (via `tokio::time::Instant`, not persisted — a restart re-triggers an immediate full sync, which is correct). `parse_target_address` accepts both bare addresses and CIDR notation. |
| `src/ipfilter.rs` | `filter_and_aggregate`: the output sanitization pipeline. Static `RFC1918`/`LOOPBACK`/`BOGONS` range tables (lazily built via `std::sync::LazyLock`), an `overlaps_any` containment check applied per configured flag, and a final `ipnet::IpNet::aggregate()` pass to collapse the survivors into the smallest equivalent CIDR set. |
| `src/vault_client.rs` | `VaultClient`: the outbound, `CANONICAL_V1`-signed HTTP client for Vault. `fetch_ips(groups, since)` builds either a full query (no `since`) or a differential one (`since=<ts>&include_deleted=true`) and deserializes Vault's `VaultApiRecord` shape (`target_address`, `updated_at` as `chrono::NaiveDateTime`, `is_deleted`). `list_groups()` (`GET /api/groups`) deserializes `VaultGroup { id, name }`, used by `api::groups::list_vault_groups`/`grant_key_group` and `groups::cleanup_stale_group_permissions`. Both share a private `signed_get<T>` helper (the signing/error-mapping logic `fetch_ips` used to inline directly). `from_config` returns `None` when `VAULT_BASE_URL`/`VAULT_API_KEY`/`VAULT_SIGNING_SECRET` aren't all set. |
| `src/sync.rs` | `spawn_sync_worker`: the background `tokio::spawn` loop (15s tick) implementing the hybrid protocol described in `README.md` — per endpoint, a full sync when 24h have elapsed (or none has ever run) and a differential sync when `ttl_seconds` has elapsed since `endpoints.last_synced_at`, updating that DB column after each successful sync and logging-and-continuing (never failing the process) when Vault is unreachable. |
| `src/groups.rs` | `spawn_group_permission_cleanup_worker`: a second background `tokio::spawn` loop (runs once at boot, then every 30 days) that removes `vault_group_permissions` rows referencing a Vault group Vault no longer has. Conservative by construction: with no Vault client configured, or a failed/unreachable `list_groups()` call, the cycle is skipped entirely — only a *successful* listing is trusted enough to say a group is really gone, per the user's explicit "don't remove group if they have no connexion" instruction. Distinct from `src/api/groups.rs` the same way `sync.rs` (background worker) is distinct from `api/endpoints.rs` (HTTP handlers) for endpoints. |
| `src/ratelimit.rs` | `RateLimiter`: the public feed's anti-DoS gate. A `Mutex`-protected `HashMap<IpAddr, Instant>` plus an insertion-ordered eviction queue, capped at `MAX_TRACKED_IPS = 10,000`, enforcing `RATE_LIMIT_WINDOW = 120s` per source IP. |
| `src/feed.rs` | `serve_feed`, the `GET /feed/v1/{token_secret}/list.txt` handler. Resolves the client IP, looks up the endpoint by token (`404` if unknown), checks `bound_ips` (async, hostname-aware via `bound_ips::is_allowed`/`state.dns_resolver` — `403` if disallowed), aggregates+filters the cached snapshot, computes the SHA-256 `ETag`, answers a matching `If-None-Match` with a free `304` (no rate-limit consumption — see the ordering rationale in the file's own doc comment), and otherwise applies the rate limiter before returning the full `text/plain` body. |

## `src/api/` — admin API (`/api/*`, behind `auth_middleware`) and probes

| File | Responsibility |
| :--- | :--- |
| `src/api/mod.rs` | Module declarations (including `groups`) and `pub use` re-exports consumed by `lib.rs`'s route table. |
| `src/api/support.rs` | Shared helpers: `generate_random_key`/`hash_key` (credential minting/lookup), `describe_resource` (renders a `kind:id (name)` audit-log target reference), and `create_audit_log` (writes one `audit_logs` row; propagates a write failure rather than swallowing it, since the mutation it follows has already committed — see its doc comment). `create_audit_log` is generic over `sea_orm::ConnectionTrait` (2026-08-19, not a concrete `&DatabaseConnection`) so a caller running a multi-step mutation inside `db.transaction(...)`/`db.begin()` (e.g. `api::keys::delete_api_key`'s endpoint reassignment) can pass the transaction handle directly, committing or rolling back the audit entry atomically with the mutation it describes. `validate_bound_ips` moved out to `bound_ips.rs` 2026-08-25 (hostname support). |
| `src/api/guards.rs` | Authorization decisions shared by more than one `api/keys.rs` handler, centralized 2026-08-19 (previously inlined per handler): `require_master`, `guard_master_delete_or_rotate` (refuses deleting/rotating the Master key), `guard_master_update` (refuses a `PUT /api/keys/{id}` touching the Master's `name`/`can_manage_keys` — `bound_ips` is the one field still changeable). Deliberately small: this crate's two-tier RBAC has no delegated-grant conjunction rules to centralize the way `example/` peers' larger `api/guards.rs` files do — see `AGENT.MD`'s "Why two tiers, not three". |
| `src/api/auth.rs` | `GET /api/auth/me` — reports the caller's own identity and RBAC flags, so the SPA (and this README's curl example) can authenticate once and introspect what it's allowed to do. |
| `src/api/keys.rs` | CRUD for `api_keys`, every route gated `require_master` (`api::guards`): `create_api_key` (mints a Daughter key, returns its plaintext secret + signing secret exactly once), `list_api_keys`, `update_api_key` (name/`bound_ips`/`can_manage_keys` — `is_master` is not a field on the payload type, so it cannot be set through the API by construction; `guard_master_update` additionally refuses a `name`/`can_manage_keys` change when the target is the Master), `rotate_api_key` (`POST .../rotate` — replaces the API key *and* signing secret; `guard_master_delete_or_rotate` refuses the Master), `rotate_signing_secret` (`POST .../rotate-secret`, ported from `simply_ip_vault`'s identical route — replaces *only* the signing secret, leaving the API key/name/`can_manage_keys` untouched; same Master guard, `KEY_SECRET_ROTATE` audit action, response is `RotateSigningSecretResponse { id, name, signing_secret }` with no `api_key` field since it never changes). `delete_api_key` (substantially rewritten): judges concurrent-delete success on `rows_affected`, not merely "the query didn't error"; if the target key owns any `endpoints` and the request carries no `?reassign_to=<key id>` (`StrictQuery<DeleteKeyQuery>`), refuses with `409` and a structured `AppError::ConflictWithDetails` inventory (`owned_endpoints: [{id, name}, ...]`) instead of silently orphaning them via the schema's `ON DELETE SET NULL`; with `reassign_to`, the reassignment (`Endpoint::update_many().col_expr(...)`, portable across SQLite/PostgreSQL/MariaDB) and the delete run inside one `state.db.begin()`/`txn.commit()` transaction, including the audit write. `CreateKeyPayload`/`UpdateKeyPayload`/`DeleteKeyQuery` all carry `#[serde(deny_unknown_fields)]` — a stray field is refused with a `400` naming it, not silently dropped. Every mutating route writes a `KEY_CREATE`/`KEY_UPDATE`/`KEY_DELETE`/`KEY_ROTATE`/`KEY_SECRET_ROTATE` audit entry after its write commits. |
| `src/api/endpoints.rs` | CRUD for `endpoints`. `create_endpoint` — any authenticated key may call it; the new row is owned by the caller. `list_endpoints` — Master sees every row, a Daughter sees only its own (`owner_key_id` filter). `update_endpoint`/`delete_endpoint` — gated by `may_manage` (Master or owner); `delete_endpoint` has the same `rows_affected`-checked concurrent-delete handling as `delete_api_key`. `reassign_endpoint_owner` — Master only. `validate_group_access` (called from both `create_endpoint` and `update_endpoint` whenever `vault_groups` is set): a no-op for Master, but for a Daughter refuses any group in the submitted `vault_groups` the caller holds no `vault_group_permissions` grant for (`api::groups::granted_group_names`), naming every ungranted group in the `403`. `CreateEndpointPayload`/`UpdateEndpointPayload`/`ReassignOwnerPayload` all carry `#[serde(deny_unknown_fields)]` (2026-08-18, same rationale as `keys.rs`). Every mutating route writes an `ENDPOINT_CREATE`/`ENDPOINT_UPDATE`/`ENDPOINT_DELETE`/`ENDPOINT_OWNER_REASSIGN` audit entry after its write commits. |
| `src/api/groups.rs` | `list_vault_groups` (`GET /api/vault-groups`, Master-only — live `VaultClient::list_groups()`), `list_key_groups` (`GET /api/keys/{id}/groups` — Master or the key itself), `grant_key_group` (`POST /api/keys/{id}/groups`, Master-only — the payload carries only `vault_group_id`; its name is resolved from a *fresh* Vault call, never trusted from the client, so a grant can't record a name that doesn't match the id and a nonexistent id is refused outright rather than silently stored; idempotent — granting an already-granted group returns the existing row, not a conflict), `revoke_key_group` (`DELETE /api/keys/{id}/groups/{permission_id}`, Master-only — the one two-path-segment route in this crate, so it takes axum's own `Path<(Uuid, Uuid)>` directly rather than `StrictPath`, which only ever wraps a single-segment `Path<Uuid>`), and `granted_group_names` (the local, no-Vault-call lookup `api::endpoints::validate_group_access` uses). Every grant/revoke writes a `KEY_GROUP_GRANT`/`KEY_GROUP_REVOKE` audit entry. |
| `src/api/audit.rs` | `GET /api/audit-logs` — lists the audit trail, most recent first, optionally filtered by exact `action` and paginated (`limit`, capped at 500; `offset`), via `StrictQuery<AuditLogQuery>` (2026-08-19; `AuditLogQuery` carries `#[serde(deny_unknown_fields)]`). Master-only: audit entries span every key and endpoint in the system, so a scoped Daughter key seeing them would be an RBAC leak regardless of what it owns. |
| `src/api/health.rs` | `health_check` (`GET /health`/`/healthz`, always `200`, no DB query) and `readiness_check` (`GET /ready`/`/readyz`, `200` only when an `api_keys` count query succeeds — an ordinary SeaORM query, not raw SQL — and `MasterPin::get()` is `Some`). Both mounted outside `auth_middleware` in `lib.rs`. |

## `static/` — embedded admin dashboard SPA

Zero external dependencies (no CDN links, no build step); served as the router's fallback service,
so any path not matched by `/health`, `/ready`, `/feed/v1/*`, or `/api/*` resolves here.
